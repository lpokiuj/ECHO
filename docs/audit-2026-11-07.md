## Fix list (priority order)

Status: items 1 (except the shared default password) and 2 are fixed; see the API PLAN Decisions
("Login hardening", "Email case"). Item 4 (CI) and tech-debt item A (docs) are done. The rest is open.

1. **Public-exposure security.** The POC script exposes the API through a tunnel.
   - No rate limiting on `POST /auth/login` (listed out of scope in the API PLAN).
   - No security headers (`helmet`). Password rule is only 8 characters.
   - One shared `DEFAULT_USER_PASSWORD` for every created or reset account. Per-user random temp
     passwords, shown once to the admin, would remove the shared secret.
   - No minimum length check on `JWT_SECRET`; `.env.example` ships `dev-only-secret-change-me`.
2. **Email is case-sensitive.** Login does `u.email = :email`, with no lowercasing or `citext`.
   `Michael@x.com` and `michael@x.com` are different accounts. Lowercase in the DTOs and add a
   unique index on `lower(email)`.
3. **Hosting.** `scripts/poc-up.sh` serves the web app with `vite preview` (not for production),
   on a random tunnel URL, only while the laptop is on. Pick a real host: static build behind
   Caddy/nginx proxying `/api`, plus a Dockerfile for the API and managed Postgres.
4. **No CI.** *(Done: `.github/workflows/ci.yml` runs API lint, unit, migrate and e2e against a
   Postgres service, then the web check and build. Not yet run on GitHub; Playwright and a coverage
   report are still to add.)* Original note: add a workflow with a Postgres service that runs lint,
   unit tests, API e2e and the web check; Playwright as a separate optional job.
5. **Backups.** The database is one Docker volume (`echo_pgdata`) on a laptop. Add scheduled dumps.
6. **Smaller items.**
   - Web unit tests spawn 20 workers at about 2.8s startup each; try `isolate: false` (watch for
     state leaking between files).
   - Several 400/409 responses lack a machine-readable `code` (see `backend-requests.md`).
   - Move the API to vitest 5 to clear the cosmetic ELSPROBLEMS.
   - Whole-collection list endpoints are fine at this size; revisit if lists grow.

## Feature ideas (by value)

1. **Notifications** (WhatsApp or email): "you were assigned" and "service time changed" (rule 14
   already plans the latter for v2). First step with no infrastructure: a WhatsApp deep link that
   prefills a message.
2. **Calendar feed (`.ics`)**: per-user subscription URL with a revocable token.
3. **Suspension** (`docs/features/11-suspension-TBD.md`). Suggested answers to its open questions:
   env vars for the parameters and a rolling window for the count, so no new table.
4. **Read recorded absences per service**: `GET /services/:id/teams/:teamId/absences` (already in
   `backend-requests.md`, medium). Today the taker's switches reset on reload.
5. **Swap requests**: a volunteer asks a teammate to cover (currently out of scope).
6. **Overlap warnings** when assigning someone to two overlapping services (listed as Later).
7. **Operations**: structured request logging and an audit log of who assigned or unassigned whom.

## Strengths worth keeping

- Assign race handled by the database: `UNIQUE (service_id, user_id)`, `ON CONFLICT DO NOTHING`,
  and advisory locks for the availability race.
- Auth loads the user on every request, so role and deactivation changes apply immediately.
- Default-deny global auth guard, real-Postgres tests with a `_test` database guard, and a seed
  that refuses production.
- A documented API contract with MSW handlers copied from it, and a no-literals test for UI text.

### New items

- **A. Doc mismatches.** *(Done.)* The `GET /me/schedule` example now matches the field table and
  the real response (`unavailable`, no `isAbsentTaker`; checked against `schedule.service.ts` and the
  e2e test). `backend-requests.md` now holds only open requests, and
  `docs/features/11-suspension-TBD.md` is tracked.
- **B. Duplicated eligibility rules.** The unavailable and already-assigned checks live in both
  `candidates()` and `assign()` (`assignments.service.ts`, about 250 lines, hand-written
  `dataSource.query` SQL). Feature 11 (suspension) would add a third copy. Extract one eligibility
  query and one skip-reason source before building it.
- **C. Test shape.** Only two API `.spec.ts` files exist (both guards); all service logic is covered
  through e2e, which needs Docker and the database. Several test files run 400 to 860 lines
  (`assignments.e2e-spec.ts` 858). Coverage is not measured; `test:cov` exists but nothing uses it.
  Add a coverage report to CI first, set a threshold after seeing the number.
- **D. Token revocation.** The guard reloads the user per request, so deactivation and role changes
  apply at once, but a token issued before a password change stays valid until `JWT_EXPIRES_IN`
  (15m). Low exposure today. Add a `passwordChangedAt` check if refresh tokens or a longer TTL arrive.
